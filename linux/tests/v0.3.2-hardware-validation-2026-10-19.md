# v0.3.2 hardware validation (2026-10-19)

Board: M5Stamp ESP32-P4 + C6 (SDIO), P4 USB Serial/JTAG on COM10.  Only the
P4 flash was written; the C6 was not touched.

v0.3.2 is v0.3.1 with the #37 root access and login records changes: `su`
with a per-device `root_password=`, root over SSH by key only, `su` logging,
live revocation of deleted key files, and utmp/wtmp with `who`, `w`, `users`
and `last`.  The kernel source, the DTB and the kernel config are those of
v0.3.1.  The checks of each change on local builds are in
`issue37-root-access-2026-10-18.md`.

## Results

The 16 MB image includes the factory drive, so the first boot was a blank-drive
first boot.  The STA settings and the m5 password were then written into the
live drive image from the serial console, and `root_password=` was replaced
with a known test value, as in the earlier records.  No password is quoted
here.

A first attempt to time the root key polled SSH every 2 s and tripped inetd's
limit (`22/tcp: too many connections, pausing`, 20 connections in 60 s); it
was repeated with single attempts.  This is the documented inetd behaviour,
not a regression.

## Not covered

- `maxcpus=2` (3 of 10 boots usable on 7.2, `v0.3.0-feature-checks-2026-10-18.md`).
- Edits from a real Windows/macOS host over USB-A (emulated by a loop mount
  of `/tmp/boot.img` on the board, as before).

A locked root at boot, wtmp rotation with the leak checks, and a full `/tmp`
ramdisk were run on this image afterwards: see
`v0.3.2-followup-checks-2026-10-19.md`.  The full ramdisk found a bug in
v0.3.2: a user can fill it, and a root key saved then is not installed
although the log says it is.  The fix is on `main` after the tag.
