# #50/#51 — NOMMU user-pool measurement + best-fit A/B (2026-10-21)

Epic #49 measurement harness (`linux/tests/nommu-mem-harness.py`) and the
first allocator experiment: `gen_pool_best_fit` (patch 0089, env-gated
`EASYSTICK_POOL_BESTFIT=1`).  Board: EasyStick Stamp-P4, serial COM10.
Images: `mem50s` = stock `11b205e`; `mem50bf` = `757ab15` + 0089.

All board-side numbers were sampled over the serial console so the harness
itself never occupies the pool.

## Network modes used

| label | board mode | session transport | pool cost per session |
|---|---|---|---|
| AP/loopback | SoftAP fallback (no WAN/STA link) | `dbclient` → 127.0.0.1 on the board | ~2× (dbclient *and* dropbear children, each is the ~610 KB multicall binary) |
| STA/LAN | station, DHCP lease on lab LAN | host `ssh` over Wi-Fi (SDIO/esp-hosted path) | ~1× (dropbear `-i` server child only) |

Why two modes: the first `mem50s` flash wrote the `boot` partition
(`0xf40000`, staged `boot.img`, crc32 `f4a7f4c4`); at the next boot the
running system committed that staged template to the live boot FS
(`generation=14 slot=0` → `generation=1 slot=1`), replacing the STA config
with the generated SoftAP.  Only AP/loopback was possible until STA was
restored at runtime via `/tmp/config.txt` (documented live-apply path —
`/boot` → `/tmp` → built-in; no flash writes, survives `S40network
restart`, gone on reboot).  `mem50bf` and all later flashes wrote **only
kernel/rootfs/dtb** (`0x90000`, `0x810000`, `0xf10000`) — never the boot
slots.

Loopback `dbclient` bytes are reported in their own row; the server-side
`dropbear -i` count is the session source of truth either way (the lab
LAN closes client TCP ~1 s in while the server child keeps its pool
pages).

## Counters

`/sys/kernel/easystick/nommu_pool`: `alloc_fail`/`fallback` are cumulative
since boot; deltas below are end−start per scenario.  Under deep pool
pressure `binfmt_flat` cannot exec even `cat`/`grep`/`ip` (contiguous
block unavailable) — the harness's hot-path readers use shell builtins
only (`exec 3< f` + sequential `read <&3`; plain `while read < file`
returns only line 1 because busybox `read` drains the whole seq_file on
the first call — see run-3 note).

## Findings

1. The ceiling is **contiguity, not capacity**.  On the 10 MiB pool,
   ~4.4 MiB is used at idle and each `dropbear -i` exec needs a
   contiguous ~614 KB text+data block inside a fragmented free space;
   N=6 always oversubscribes.
2. Under pressure `binfmt_flat` execs fail with errno -12 even for
   `cat`/`grep` — the kernel log lines `nommu: Allocation of length
   614400 from process … (dropbear) failed` / `491520 … (grep)` were
   captured live during run2.
3. First-fit vs best-fit: see the A/B table in the report — best-fit
   keeps `largest_free` slightly higher under session load
   (STA: 4 held, lf 135 KiB; AP: lf 1.32 MiB at 2–3 pairs) but does not
   eliminate exec ENOMEM at N=6 on the 10 MiB pool.  (The 4/6 count is
   that run's outcome, not a ceiling — the corrected R2 rerun packed
   6/6; session count at N=6 is packing luck at the boundary.  See
   Round 2 for the stable discriminators: `largest_free` floor and
   `alloc_fail` Δ under scenario A.)
4. The i40b +2 MiB `MemFree` drop (≈6.9 → ~1.84–4.0 MB) is the reserved
   region itself: the enlarged `linux_nommu_pool_low` is carved out of
   kernel RAM at boot, so `MemFree` falls by ~2 MiB.  wget→/dev/null
   writes no page cache (no destination file); identical-harness wget
   runs show only small Slab deltas — cache is not the cause.
5. Run3's all-`-` output was a harness reader bug (`while read` gets one
   line of a seq_file), not a board regression — fixed by fd-held
   sequential `read <&3` (commit `718422f`).

### R2.3 — harness fixes (`fbaa2b3`, `acf89b7`, `05b481e`)

- **settled-idle gate** — idle snapshot only after uptime ≥ 45 s
  *and* the same PID set is seen twice 10 s apart (`wait_settled`).
- **alloc_fail attribution** — dmesg `Allocation of length N from
  process PID (comm) failed` lines are tallied per scenario window
  into per-comm tables classified system / user / unclassified
  (`sh` counts user — console/session shells; S40network's own execs
  are system).
- **exec-free readers** on all hot paths — FD-held sequential
  `read <&3`; busybox `read` drains a whole sysfs seq_file on the
  first call, and under pressure execs fail anyway.
- **net check** via `/sys/class/net/wlan0/operstate`
  (`up`/`dormant` = recovered) — no `ip` exec needed.
- host ssh: a default key argument, `UserKnownHostsFile=/dev/null`
  (the board regenerates its host key every boot), and ASCII-safe
  prints — an em-dash in the attribution header crashed `scenario:all`
  mid-run on this cp932 console before `05b481e`.

**Orphan experiment (review item 3).**  Real interactive `ssh -tt`
sessions are *refused* by `dropbear -i`: the PTY request gets the
connection closed — devpts/ptmx exist on-board, so noted as a product
limitation (PTY-less sessions only).  Server side: killing the client
of a live `-T` session removes the on-board `dropbear -i` within
seconds — **no server-side orphan/leak over LAN**.  inetd `-R 10`
(10 conns/min) was observed throttling the probes during testing and
is now documented; inetd-mode session lifetime = remote command
duration.  Per-session pool cost in STA (item 4): **~1.17 MB** per
LAN host-ssh session (dropbear child only).  AP/loopback `dbclient`
sessions cost ~2× because `dbclient` is the same ~610 KB multicall

### R2.4 — patch 0090: user-alloc reserve (watermark), measured

`linux/kernel-patches/0090-easystick-nommu-user-reserve.patch`, gated
`EASYSTICK_USER_RESERVE=1` in `build-m1.sh`, registered next to
0089's `EASYSTICK_POOL_BESTFIT` (the two compose — the reserve+bf arm
has both gates on).  **One pool, no split:**

- user mark decided at alloc time — controlling tty == `ttyGS1`
  (the askfirst console shell and everything it runs) OR own/ancestor
  comm == `dropbear` (inetd spawns `dropbear -i` per session; exec
  sets comm so the session dropbear's own image load marks too).
  `PF_KTHREAD` excluded; inheritance across fork/exec is free.
- a marked alloc must leave ≥ `user_reserve_contig` (default
  1,228,800) contiguous free AND ≥ `user_reserve_total` (default
  2,097,152) total free afterwards, else it is refused and falls
  back to buddy (`pool_fallback` + `user_denied` both count).
- system allocs ungated; `system_alloc_fail` counts unmarked-task
  pool failures on its own counter.
- sysfs `/sys/kernel/easystick/`: `user_reserve_contig` /
  `user_reserve_total` RW (0 disables the gate), `user_denied` /
  `system_alloc_fail` RO, same four fields in the `nommu_pool`
  aggregate node.
- The optional ≥128 KB high/low region routing was skipped — the
  `gen_pool` algo hook selects within a chunk, not across regions.
- Build note: reserve images REQUIRE `--profile m3-lab` — the dw-mmc
  patch series (incl. 0087's prerequisites) is gated on
  `network_profile`; without it linux-headers patching fails at 0087.

### Assessment (R2)

The reserve meets the #51 acceptance bar: **system-side alloc
failures ~0–1** while opening 6 sessions and through all 5 restarts
(vs 4 system fails for stock R2, and **+119 scen-A Δ** for the
corrected best-fit run — mostly unclassified udhcpc/S40network
script execs); **≥4 user sessions held** — 5/6 on both reserve arms,
the denied 6th landing in buddy RAM (bf's 6/6 this run vs 5/6 stock
is luck-of-packing at the boundary — the earlier bf run held 4/6 —
and is not the metric that matters; the churn numbers are);
**no restart-recovery regression** (18.2–18.3 s on every arm).

buddy instead of spending the reserve.  If one variant is taken:
**reserve+bf** — 5/6 sessions with the denied 6th on buddy, highest

## Round 3 re-measurement (review corrections applied)

Same board, STA/LAN, host-SSH transport, N=6, scenario A.  Harness
changes first: (1) the `Allocation of length N ... failed` line fires
at `mm/nommu.c`'s `enomem:` path, reached only when BOTH the userspace
pool and the buddy fallback failed — every such dmesg line is a real
ENOMEM (exec/mmap actually failed), not a pool miss.  `alloc_fail`
remains the pool-miss counter and can include reserve-gate denials
that buddy later serves.  (2) side attribution is by PID ancestry —
`/proc/<pid>/stat` ppid chain walked to init; ttyGS1 controlling tty
or a dropbear ancestor = user (the same rule 0090 applies in-kernel);
reaching init = system; unreadable = exited-before-read (counted
separately; no comm-name lists anywhere).  (3) MemFree/MemAvailable
minima and `user_denied`/`system_alloc_fail` deltas tracked through
scenario A.

Reading the real ENOMEMs: every failing comm (`exe`, `ifconfig`,
`route`, `default.script`, `rm`, `mv`, `sed`, `sh`, `sleep`,
`S40network`, `udhcpc`) is a transient udhcpc/S40network restart
child or harness pipeline exec — all `exited` before `/proc` could
be read, which is the expected bucket for short-lived processes
(classification runs after the fact).  On the reserve arms the
scenario-A restarts are spawned from the ttyGS1 console shell, so
the entire restart subtree is user-marked under 0090's ancestry
rule: those allocs hit the gate → `user_denied` (+307/+396) → buddy
fallback → real ENOMEM only where buddy was also short.  That is
why `system_alloc_fail` stayed 0 while dmesg still showed ENOMEMs —
the fails landed on user-marked transients by design.  On stock and
bf the same churn failed straight from the pool (alloc_fail +98/+165
counted pool misses; the 56/40 dmesg lines are the subset where
buddy could not cover either).

higher at the trough (5.5 vs 4.1 MB) and never logged page-allocation
failures, SKB warnings, or OOM in dmesg on any arm.  `user_denied`
is a count, not bytes — patch 0090 records no per-alloc size for
denials, so exact bytes pushed to buddy are not derivable; scale is
hundreds of denied allocations of typical exec size (~100–500 KB).

## Round 4 — explicit system mark (patch 0091 + easystick-sys + netreq)

### Mechanism

- `PF_EASYSTICK_SYSTEM` = `0x40000000` (the `PF__HOLE__40000000` slot),
  set/cleared by `prctl(PR_EASYSTICK_SYSTEM=0x45535459, 0|1)`, root only
  (`CAP_SYS_ADMIN`), both directions allowed; `copy_flags()` keeps it on
  fork, exec preserves it; visible in `/proc/<pid>/stat` field 9.
- `0090`'s `nommu_task_is_user()` checks the flag before the ctty/ancestor
  tests — flag wins, task is system-side.
- `/usr/sbin/easystick-sys [-u] CMD...` (new package): prctl + exec.
  Kernels without the option return EINVAL and the command still runs;
  exec failure exits 111 so callers can fall back to unmarked execution.
- `S40network`, `S85easystick-ssh`, `S90easystick-watchdog` re-run once
  through `easystick-sys` (one-shot via `ES_SYSMARK`), so a console/SSH
  start no longer leaves the subtree user-marked.  `S45bootsync` needs
  nothing — bootsync is init-respawned, so it already has init ancestry.
- `inetd.conf` wraps each per-connection handler in `easystick-sys -u`:
  a flag-marked inetd (e.g. user-started S85 restart) would otherwise
  mark dropbear *and its sessions* system via fork inheritance, defeating
  the user gate.  With `-u`, dropbear/session children classify by
  ancestry again (dropbear ancestor => user).
- Scenario A trigger modes: `A-user` = console `S40network restart`
  (unchanged, user ancestry); `A-system` = `echo restart >
  /run/.es-netreq`, which init-ancestry `easystick-bootsync` polls and
  runs — the product path classification without any boot.img/flash
  write.
- Harness `classify_pids()` now checks the leaf's flag first
  (`system(flag)`); leaf-only because the flag is fork-inherited and
  per-connection dropbear deliberately clears it.

## Round 5 — sysmark exec fix + transient sizing + reserve sweep

Image `mem50r5`: EASYSTICK_POOL_BESTFIT=1 + EASYSTICK_USER_RESERVE=1 +
EASYSTICK_USER_SYSMARK=1, m3-lab profile.  Implementation history squashed:
58715a4+19b0182+9db1185 folded into the 19d2360-based commit (`abbbced`);
round-5 fixes in `c952c02`, syspeak harness in `5636298`/`de4720f`/`460ffc6`.

### Code fixes

- `S40network`/`S85easystick-ssh`/`S90easystick-watchdog` now do
  `ES_SYSMARK=1 exec /usr/sbin/easystick-sys "$0" "$@"`: the mark re-run
  *replaces* the shell instead of leaving the ~725 KB script shell resident
  beside the marked copy for the whole restart.  R4's A-system 11-ENOMEM
  residual was that doubled shell pushing the restart peak over the line.
- `easystick-bootsync` `netreq_check()` allowlists verbs: apply*/reload*/
  restart*/start*/stop* only; anything else is logged
  (`network request: ignoring unknown verb`) and skipped — no more silent
  fallthrough to `apply`.
- Harness: `--rcontig/--rtotal` write the 0090 sysfs knobs per run; new
  `syspeak` scenario runs board-side samplers (used@~12 Hz via
  /proc/uptime busy-wait pacing; per-pid /proc/*/maps sweeps at ~3 s) and
  reports flag-classified transient demand; `_ssh_probe` retries (4x/3 s).

### Reading

- **The exec fix eliminated the A-system residual**: system-side real
  ENOMEM went 11 (R4, child-invocation) -> 0 on every arm.  The doubled
  shell was indeed the extra ~0.7 MB that pushed the peak over.
- **Bigger reserves buy nothing system-side** — system pool misses are 0
  (or buddy-served) on all arms — **and cost user capacity**: sessions
  landed drop 4 -> 1 and user ENOMEM grows 2 -> 6 as the reserve grows.
  The syspeak-derived 2 MB/3 MB and the reviewer-suggested 2 MB/3.5 MB
  both strictly lose to the current defaults on this workload.
- Recommendation: **keep 1200 KiB contig / 2 MiB total** — post-fix the
  restart transient serializes under what the gate already leaves.
- user_denied (5-14/run) is the gate refusing session-subtree execs near
  the watermark — the intended behaviour, not an error.

### New transient issue found (flagged, not root-caused here)

For a window after restart churn (and sometimes early boot), new SSH
session execs die post-auth: server closes the connection after the exec
request is accepted.  dmesg shows an instruction-fetch fault
(`Unable to access instruction at 0x8b920350`, RISC-V-style reg dump) —
the session child crashes, consistent with a vfork/exec corruption path.
`user_denied` does NOT bump — not the reserve gate.  Self-heals in
~3-6 min; reboot clears it.  In one instance userspace froze entirely
(serial console + ssh dead, kernel still answering ping — a kthread
watchdog means no reset) and /dev/ttyGS1 re-enumerated mid-window
(node timestamp 03:48 on a 03:21 boot), which took the console shell
down with it.  Provenance unknown — possibly pre-dates the patches
(M2.5 ledger work already saw post-auth hangs); needs an
EASYSTICK_SSH_LEDGER=1 build to localize.  Harness `_ssh_probe` retries
(4x/3 s) mask this at the readiness check, and server-side session counts
are the load figure as before.
