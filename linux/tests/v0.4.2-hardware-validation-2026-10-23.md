# v0.4.2 hardware validation (2026-10-23)

Board: M5Stamp ESP32-P4 + C6 (SDIO), P4 USB Serial/JTAG on COM10.  Only the
P4 flash was written; the C6 was not touched.

v0.4.2 is v0.4.1 with the NOMMU pool reserve (#51, #50: best-fit `0089`,
user reserve `0090`, system mark `0091`, `run-system`), the dropbear
fixes for #54 (256 KB stack, `0012` vfork-child hardening), and a flash
script that leaves the boot slots alone by default.  The release build sets
`NOMMU_POOL_BESTFIT=1`, `NOMMU_USER_RESERVE=1` and
`NOMMU_SYSTEM_MARK=1`.  The measurements behind the allocator are in
`issue50-51-memory-2026-10-21.md`.

The earlier runs on the same sources (images mem50r5 and mem50r8, Devin's
rounds 5–7 in issue #50) cover the rest: `check-boot-log.py` 13/13, the host
tests, USB update, `config.txt` apply, STA, SSH/scp, autorun, and a 30-minute
soak with `alloc_fail` 0 and `system_alloc_fail` 0.  The restart peak test
(5 restarts with 6 SSH sessions held) gave 0 real out-of-memory failures in
the system's own programs on every arm.

## Not covered

- The CI image itself was not run through `check-boot-log.py`, the soak or
  the USB update; the mem50r5/r8 runs above stand in for them.  The CI image
  differs from them only in the build environment.
- AP mode was checked from the board side only (SoftAP started, `udhcpd`
  serving); no client joined it.
- The 16 MB image was not flashed, so its blank-drive first boot was not
  repeated; the factory drive and boot-shim first-boot code did not change
  since v0.4.0.
- One board reset at about 5.4 ks of uptime during an idle window in round
  7 (pstore empty).  It lined up with a COM10 attach in that session, but
  that was not proven.
- Each SSH session now costs about 224 KB more pool because of the 256 KB
  dropbear stack (#52 will measure and shrink it).
