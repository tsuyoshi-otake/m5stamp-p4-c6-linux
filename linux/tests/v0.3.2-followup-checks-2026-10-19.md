# v0.3.2 follow-up checks (2026-10-19)

The items that `v0.3.2-hardware-validation-2026-10-19.md` left as "not
covered", run on the released v0.3.2 image (CI run 39177051318, flashed as
downloaded), and a fix for what they found, checked on a local build.

Board: M5Stamp ESP32-P4 + C6 (SDIO), P4 USB Serial/JTAG on COM10.  Only the
P4 flash was written; the C6 was not touched.  STA mode; the SSH client is
the test PC.  No password is quoted here.

## On the v0.3.2 release image

### Locked root at boot

| Check | Result |
|---|---|
| `root_password=short` saved to the drive, then reset | 11/11; `ES_CREDENTIALS: root_password= must be 8-64 characters; root login stays locked`; `/etc/shadow` has `root:!` |
| `su` as m5 with the old (right) password | `su: incorrect password` after 3.1 s; logged as `su: - pts/0 m5:root` |
| `su` with a wrong password | the same, 3.2 s |
| A valid `root_password=` saved to the live drive | `root password applied` a few seconds later, without a reboot; `su` gives a root shell, logged as `su: +` |

### wtmp rotation and leaks

`rottest.sh` (as in `issue37-root-access-2026-10-18.md`) from 8 records after
boot: 2 held sessions, 2 × 18 paced logins, then 8 at once (100 records).

| Check | Result |
|---|---|
| Before the burst | `wtmp` 32256 bytes (84 records), `wtmp.1` empty |
| After the burst | `wtmp.1` 32640 bytes (85 records), `wtmp` 5760 bytes (15 records): 100, none lost, both multiples of 384; no `wtmpx` warning |
| Pool / processes / fds, before and after the 46 logins | 6488K / 48 / 64 both times; `utmp` 3072 bytes (8 slots) |

### Full /tmp ramdisk

`/tmp` is a 1979 KB ext2 ramdisk shared with `/home`, `/root`, `/var/lib` and
`/var/log`.  The release formats it with `mke2fs -m 0`, so there are no
reserved blocks: user `m5` filled it to 100% with one `dd` (1660 KB), and a
root `dd` afterwards got nothing more.  `/tmp/boot.img` (the USB drive) is
allocated in full at boot and the bootsync stage is on `/run`, so the drive
itself was not affected.

| Check, with `/tmp` full | Result |
|---|---|
| Password SSH logins with a pty, as m5 | work; Dropbear logs `wtmpx_write: problem writing /var/log/wtmp: No space left on device` and truncates the short record, so `wtmp` stays a multiple of 384; recording resumes once space is freed |
| `ssh host cmd`, `who`, `last` | work; a write to `/tmp` fails with `No space left on device` |
| `su` | works and is logged |
| Drive saves (`Saved to flash`), `credentials.txt` and `config.txt` changes | saved to flash; the new `credentials.txt` and `config.txt` reached `/tmp` (they fit in their existing 1 KB blocks); passwords applied |
| Deleting `root_authorized_keys` | `keys for root revoked` (needs no space) |
| Saving `root_authorized_keys` | **bug**: `mkdir: can't create directory '/root/.ssh': No space left on device`, yet the log said `ES_SSH_KEYS:  key(s) installed for root` with an empty count; no key was installed |
| After `rm` of the fill files | logins recorded again; a key save installs the key |

So a user could fill the ramdisk and stop root's key updates, and the log
then claimed success.

### Other observations

- During one of these saves, `config.txt` changed and bootsync reloaded the
  network while a console pipeline of about ten commands ran.  Several
  execs failed for a few seconds with `nommu: Allocation of length 491520
  ... failed` (`grep`, `head`, `cut`, `xargs`).  The network came back by
  itself (same address; new `wpa_supplicant` and `udhcpc`).  This is the
  known pool limit (each BusyBox process takes about 480 KB,
  `v0.3.0-feature-checks-2026-10-18.md`), not a result of the full ramdisk:
  it happened after the space had been freed.
- bootsync reloads the network for any `config.txt` change except
  `autorun` lines, including `ssh_password_auth=`, which is read only at
  boot.  Harmless, but it makes such a save heavier than needed.

## Fix (9072ad7, a4d2cd0)

- `S05easystick-tmpfs` formats the ramdisk with `mke2fs -m 2`: 40 blocks are
  reserved for root, so a user cannot fill it completely.
- `credentials.sh`: `install_keys` and `install_root_keys` share
  `es_install_keys`, which writes the keys, compares the size with what was
  meant to be written, and on a short or failed write removes the file and
  logs `ES_SSH_KEYS FAIL: cannot write ... (is /tmp full?); no keys for ...
  until the next save or boot`.  The file is removed rather than kept, so
  keys taken out of the drive file never stay valid.

Before the build, the new `credentials.sh` was sourced on the v0.3.2 board
with a full `/tmp`: with no `.ssh` it logged `ES_SSH_KEYS FAIL` and left no
file; with an old one-key file and a new 15-key file (1335 bytes, more than
one block) it logged `FAIL` and removed the old file (root key refused);
after freeing space it installed all 15 keys.

The fix is on `main` after the v0.3.2 tag; v0.3.2 itself keeps the
behaviour described above.

## Not covered

- `wtmp.1` rotation with a full ramdisk.  `wtmp.1` is truncated before the
  copy, which frees as many blocks as the copy needs, so it should fit; if
  another writer took them first, the old records would be lost, as noted in
  the leak review.
- A user filling the ramdisk still stops the login records (Dropbear writes
  them as the user with group `utmp`, which cannot use root's reserve).
  `wtmp` stays consistent and recording resumes when space is freed.
