## CRLF `main.sh`: hush + uClibc glob()

`autorun_stage` strips CR from the staged scripts with
`for f in "$AUTORUN_NEW"/*.sh`, and `AUTORUN_NEW` is `/run/.autorun-new`.
On the board (root shell):

```
d=/run/a-b; e=/run/a_b          # both directories hold f.sh
echo "$d"/*        -> /run/a-b/*        not expanded
echo $d/*          -> /run/a-b/f.sh
echo "$e"/*        -> /run/a_b/f.sh
echo '/run/a-b'/*  -> /run/a-b/*        not expanded
```

`/bin/sh` is BusyBox 1.37 hush (`CONFIG_SH_IS_HUSH=y`; ash depends on
`!NOMMU`).  hush escapes a quoted `-` as `\-` (`o_addQchr()`) and calls libc
`glob()`; uClibc-ng 1.0.57 `glob()` does not unescape the directory part, so
it opens `/run/.autorun\-new` and returns `GLOB_NOMATCH`.  BusyBox describes
the same uClibc bug in a comment in `shell/ash.c`; hush has no guard for it.
The loop has never run since it was added with #34 (in v0.2.5 and v0.3.0).
An earlier manual test passed only because it used a directory without a
`-`.

Fix (1d8cc22): `for f in $AUTORUN_NEW/*.sh` unquoted (no spaces in the path),
pinned in `test-boot-config-contract.py`.  No other on-board glob has a
quoted directory part with a `-`.  On the fixed image a CRLF `main.sh` ran
both after a live save and at boot (`main.sh start m5`, then its output).

## Concurrent SSH sessions and the NOMMU pool

Twenty `sleep 60 &` as root: the first lands in the 6 MB region (registered
last, so gen_pool tries it first), the next eight fill the 4 MB region at
0x495af000, the next five come from the buddy allocator, the rest fail
(`Allocation of length 491520`).  Both pool regions serve allocations on 7.2.

| State | Method | Sessions held for 100 s |
|---|---|---|
| right after boot (`watchdog=1` feeder running) | key auth, 10 sessions 4 s apart, `echo up; read -t 100 x; echo done` | 7 (then Dropbear's 614400-byte allocation fails) |
| after 30+ min of tests | same with `sleep 100` | 4 |

Once the pool is full, `do_mmap_private()` falls back to
`alloc_pages_exact()`, so the count depends on buddy fragmentation.  The
`echo ok; sleep 100` method of `busybox-daemons-2026-10-16.md` overcounts:
when only the `sleep` exec fails, the session ends at once and frees its
memory (here it showed 10/10).  `sleep` also adds about 480 KB per session,
so those numbers and these are not directly comparable.  Count sessions
that stay open, and wait with the `read -t` builtin.

## 30-minute soak (fixed image, `maxcpus=1`)

19:04–19:34, board up 37 min at the start.  `main.py` from the drive ran
under autorun the whole time (a JSON line every 5 s).  From the PC: an SSH
login as m5 every 60 s logging memory, load, `carrier_changes` and the
autorun state, with a 10 MB `wget` (http://speedtest.tele2.net/10MB.zip)
every fifth round; `ping -n 1800` in parallel; the serial console open.

| Check | Result |
|---|---|
| SSH rounds | 30/30 |
| 10 MB `wget` | 6/6 exit 0, 48–62 s each |
| `carrier_changes` | 0 throughout |
| autorun | running throughout, tick 7 → 355 with no gap |
| MemAvailable | 6232 → 6200 kB; buddy order 7/8 blocks 1/2 from round 1 on |
| ping from the PC | 1800/1800, 4–564 ms, average 103 ms |
| serial console | nothing printed after the port opened |
| `dmesg` (cleared before the soak) | `dw_mmc 50083000.mmc: Unexpected interrupt latency` once, and the watchdog feed count line |

The dw_mmc line comes from `dw_mci_cto_timer()`: the command-timeout timer
fired while CMD_DONE was already pending, that is, the interrupt was taken
late once.  The driver only warns and the transfer goes on.  It was not seen
in the earlier records.
