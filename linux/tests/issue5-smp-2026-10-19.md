# #5: both CPUs on by default (2026-10-19/20)

Issue #5 is the `maxcpus=2` hang: CPU1 stops taking any interrupt (no tick,
no IPI) a few seconds into boot, RCU stalls follow and the board hangs.  It
was closed on 2026-10-14 as a silicon latch.  This record covers the capture
that found the trigger, the fix 0079 (which the 1-CPU image needs as well),
a console race that two CPUs exposed (fixed by 0080), two defects that
programs crashing in a loop exposed (a core lockup fixed by 0081, which the
1-CPU image needs as well, and a kernel panic on CPU1 fixed in the
boot-shim), USB drive saves that rebooted a 2-CPU board (fixed in 0072),
and the checks behind making `maxcpus=2` the default.

Board: M5Stamp ESP32-P4 + C6 (SDIO), P4 USB Serial/JTAG on COM10.  Only the
P4 flash was written, with `flash-candidate.ps1 -PreserveBoot`; the C6 was
not touched.  No SSID, PSK, password or client address is quoted here.

## Capture (smp5-e1)

0077 records every trap entry, every mret and every accepted interrupt in
per-CPU rings from entry.S; CPU0 dumps them when CPU1's tick stamp is 2 s old.

- 5 of 11 boots went deaf, 2.7 s to 32 s after the kernel started.
- `es_mret_bad_mpil=0` on all five: no mret ever wrote a nonzero MPIL, so the
  stale-MPIL hypothesis is out.
- On all five, the last interrupt CPU1 accepted was taken from user mode, and
  the next mret on CPU1 had `mcause.INT=0` (a system call or fork return) and
  returned to another task (its `tp` differs).  Within the rings this pairing
  occurs once per boot.
- CPU1 kept trapping afterwards (ecall and mret, 18 to 300 times on boots 5,
  6 and 9): exceptions still work, only interrupts do not.  CLIC slots 20/23
  stayed pending + enabled at level 0xff with `mip=0`.
- On boots 0 and 7 one trap record is missing before CPU1 enters idle.  This
  is not explained, but it does not contradict the hypothesis.

## Mechanism

This CLIC raises `mintstatus.mil` to the level of an accepted interrupt and
lowers it again only on an mret with `mcause.INT=1`.  An interrupt taken from
user mode can end in `schedule()` on its way out; the hart's next mret then
belongs to another task and has `INT=0`, or there is none at all (kernel
thread, idle).  `mil` stays at 0xff and every interrupt is masked by level
until the preempted task returns through its own interrupt frame.

- If that task resumes on the same CPU, its mret lowers `mil` and the CPU
  hears interrupts again: a deaf window, not a hang.
- The CPU stays deaf for good if the task never comes back to it: it
  migrates to the other CPU, it is stopped (SIGSTOP, Ctrl-Z, ptrace), or it
  dies first (a fatal signal is handled on the way back to user mode, so the
  frame is never returned through).  The last two need only one CPU.
- If the CPU meanwhile runs a task that came in through an `INT=0` path and
  never traps (a busy loop), the deafness lasts as long as that loop, because
  the timer interrupt that would preempt it is the one being masked.
- A caught signal is not a trigger: the handler is entered through the
  interrupt frame's own mret, which still has `INT=1`.

Upstream (`vendor/why2025-linux/docs/KNOWN-ISSUES.md`) blames an interrupt
that coincides with a privilege-dropping mret and works around it with
M-mode userspace (0031, applied here).  Every mret on this port is M to M
and the hart still latched.

## Fix 0079 (now the default; `EASYSTICK_C68_IRQ_LEVEL0=0` leaves it out)

Right after the interrupt frame is saved and before `do_irq`, entry.S runs
one mret to the next instruction with `mcause` = INT=1, MPP=M, MPIE=0,
MPIL=0.  That drops `mil` to 0 at entry, so a frame that is abandoned later
holds no level.  MIE stays 0, so `do_irq` still runs with interrupts off;
the exit path rewrites mepc and mcause from pt_regs as before.  It costs
about ten instructions per interrupt.

### Console replay on two CPUs (fixed by 0080)

The replayed block was the last ~1.4 KB of console output followed by
~2.6–3.2 KB of NUL bytes, i.e. the whole 4 KiB `xmit` ring.  Just before the
loop started, bytes were doubled and dropped: `stops writing` came out as
`stoosswwiiiig`, and `GOTGCTL=0x00090000` as `GOTGCTL==xx00990000`.

The USB Serial/JTAG ACM driver (patch 0000) drained `xmit` from its
interrupt handler (`esp32s3_acm_txint` → `uart_port_tx_limited` →
`kfifo_get`) without `port->lock`, while `start_tx` drained it under the lock
from the other CPU.  Both read and advanced the same `out` index, so bytes
were sent twice or skipped.  When both took the last byte, `out` ended up
one past `in`, and `kfifo_len()` (`in - out`, unsigned) read about 4 G: the
handler never saw an empty buffer and kept re-sending the ring.  With one
CPU the handler and `start_tx` cannot overlap (`start_tx` runs with
interrupts off), which is why this never showed before.

0080 takes `port->lock` (irqsave) around the transmit in the handler, as the
serial core requires and as `esp32_uart.c` already does.  `console_write`
does not touch `xmit`, so it is not part of the race.

### Console under load (not SMP-specific)

A test that wrote 18 bursts of 80 lines to ttyGS1 while another task
flooded the kernel log through `/dev/kmsg` (smp-def) showed two small
console defects.  Both are in code that runs the same way on one CPU.

- The end of a burst waited half a second.  The final `\r\n` of every burst
  arrived 0.5 to 0.6 s late, and the port's `tx` count went up by 2 at that
  point without an ACM interrupt.  When the IN endpoint is busy,
  `esp32s3_acm_transmit_buffer()` returns without arming the IN-empty
  interrupt, so the rest of `xmit` waits until the serial core's runtime PM
  (500 ms autosuspend) calls `start_tx` again.  The bytes are delayed, not
  lost; arming the interrupt there would fix it.
- One kernel-log line lost a character (`uvwyz`).  The console write path
  waits at most 2 ms for room in the 64-byte FIFO and then drops the
  character (0062, which replaced a 1 s wait that froze `vi`).  That is the
  likely cause.

Both are fixed by 0082 (#42, `issue41-44-2026-10-20.md`).

## User faults lock the core up (0081)

The MicroPython crash above is a user store to address 0.  To see what such
faults do, a test program (`faulter`, not part of the image) pinned to one
CPU takes 200,000 of them in a row: a 64-byte `memset()` at address 0, caught
by a SIGSEGV handler that `siglongjmp`s out.  A variant takes 20,000
unhandled ones in `vfork()` children, which the kernel kills.  One of these
loads runs beside it:

- a 1 µs `nanosleep()` loop on the same CPU;
- a `sched_yield()` loop on the same CPU, with the faulter yielding after
  every fault;
- a FIFO ping-pong with one end on each CPU;
- SIGALRM every 50 µs in the faulter, with nothing else on its CPU;
- a load on the other CPU only: ping-pong, cache maintenance, signals, a spin
  loop or memory traffic.

In most runs a second instance on the other CPU logs the faulting CPU's PC
twice a second from the ASSIST_DEBUG PC recorder.

### Symptom (smp-def, v0.3.2)

On smp-def, CPU0:

- Next to the `nanosleep()` loop, the `sched_yield()` loop or the ping-pong,
  the memset faults stopped CPU0.  Where the watcher ran, it saw CPU0's PC
  fixed on the faulting store within a second, with
  `LASTPC_BEFORE_EXCEPTION` on the instruction executed before it.  It
  stayed there for one to two minutes, until the MWDT reset the chip.  The
  vfork children next to the `nanosleep()` loop did the same, on a child's
  store.
- With SIGALRM only, or with a load on the other CPU only, all 200,000
  faults completed (13.40 s with SIGALRM).

On CPU1 (memset faults next to the `nanosleep()` loop twice, next to the
ping-pong once) the outcome varied.  Twice CPU0 reported an RCU stall on
CPU1 20 s in, the console went quiet 10 s later, and the MWDT reset the chip
at about 80 s with Core1's saved PC in user code.  Once CPU0 ran on: the
watcher logged CPU1's PC on a store in `memset()` for 200 s, and the run
neither finished nor reset.  These runs predate the CPU1 protection fix below.

The released 1-CPU image is affected too.  On v0.3.2, memset faults next to
the `sched_yield()` loop stopped the console mid-line 1 s in.  The MWDT
reset the chip 103 s later (`rst:0x7`), with Core0's saved PC on the store in
`memset()`.  Unhandled faults in vfork children next to the `nanosleep()`
loop ended the same way after 78 s, with the PC on the child's store.

### Mechanism

The core sets MEXSTATUS.EXPT_VLD (custom CSR 0x7e1, bit 5, named in
ESP-IDF's `riscv/encoding.h`) when it takes an exception.  An exception
other than ecall that is taken while the bit is set is a double exception.
The core locks up at the faulting instruction and takes no interrupt; with
`LP_CLKRST HPCORE*_LOCKUP_RESET_EN` at its default 0, only the MWDT gets the
chip back.

User code runs in M-mode on this port (0031), so the faulter can read the
CSR.  Reading it 100 times per iteration, without faults, gave these counts
of reads that found the bit set (20 million reads each):

| Load on the same CPU | smp-def | v0.3.2 | smp-expt | smp-prot |
|---|---|---|---|---|
| `nanosleep()` loop | 18,958,074 | 18,666,120 | 0 on CPU0 and CPU1 | 0 on CPU0 and CPU1 |
| `sched_yield()` loop | 4,498 | – | 0 | – |
| SIGALRM every 50 µs | 0 | – | – | – |
| none (300 million reads) | 0 | 0 | – | – |

`csrc` does not clear the bit.  With a `csrc` before every iteration next
to the `nanosleep()` loop, the reads still found it set 18,645,237 times in
20.2 million, and the re-read right after the `csrc` 184,595 times.  With an
mret with `mcause.INT=0` to the next instruction instead, they found it set
10,811 times, and it was clear after every mret.  So only the return from
an exception clears the bit.  When a system call
ends in `schedule()` and the next task resumes from an interrupt frame, that
mret has `INT=1`, and the task runs on with the bit set until its next
system call.  A fault before then locks the core up.  A task that sleeps or
yields on the same CPU makes that switch all the time; SIGALRM alone never
does.  Clearing the bit from user space is no fix: with a clear before every
fault, by `csrc` or by the mret, memset faults next to the `sched_yield()`
loop still locked CPU0 up, since a switch can come between the clear and
the fault.

### Fix 0081 (default; `EASYSTICK_C68_EXPT_CLEAR=0` leaves it out)

At exception entry, once the frame is saved, entry.S runs one mret to the
next instruction with `mcause` = INT=0, MPP=M, MPIE=0.  That clears
EXPT_VLD.  MIE stays 0 and the CLIC level is unchanged, and the exit path
rewrites mepc and mcause from pt_regs as before.  It is the exception-side
counterpart of 0079, which runs an `INT=1` mret at interrupt entry.  The bit
is now also clear while the kernel runs a system call, so an exception that
the kernel takes there itself (a WARN's `ebreak`) is no longer a double
exception.  That part is not tested.

## User faults on CPU1 panic the kernel (fixed in the boot-shim)

With 0081, every faulting run on CPU1 still ended in a kernel panic, also
with no other load (memset faults alone, twice on smp-def and twice on
smp-expt, 1 to 9 s in):

```
Oops - store (or AMO) access fault [#1]
CPU: 1 UID: 0 PID: 342 Comm: faulter Tainted: G           O        7.2.11 #1 NONE
epc : 48314ac4 ra : 49ad8a02 sp : 49aebd40
status: 00001800 badaddr: 00000000 cause: 30000007
Kernel panic - not syncing: Fatal exception in interrupt
```

The MWDT reset the chip 5 s later.  `epc` is `handle_exception+4`, the
instruction after `csrrw tp, mscratch, tp` at trap entry, while `ra` and `sp`
are the faulter's.  The store fault arrived after the core had already
entered the trap handler for something else, so the kernel took it for a
fault in its own code.

A SIGSEGV handler that returns (through `rt_sigreturn` and an mret) onto the
faulting store every other time, and steps over it otherwise, shows the
timing.  A fault reported at the store takes two faults per iteration; a
fault reported after the store takes one.  20,000 iterations took 40,000
faults on CPU0 and 20,000 on CPU1.

ESP-IDF sets each core's memory protection (PMA and PMP) in
`esp_cpu_configure_region_protection()`, for CPU1 from `call_start_cpu1()`.
The boot-shim is built with `CONFIG_ESP_SYSTEM_SINGLE_CORE_MODE` and starts
CPU1 on its own path (`c68_secondary_entry`), so this never ran on CPU1.
CPU1 kept the ROM's setup: PMA entries 0 to 14 off, entry 15 RWX over
0x40000000-0x4fffffff, and an open PMP.  On CPU0, ESP-IDF's PMA entry 0
makes 0x00000000-0x1fffffff inaccessible.  A store to address 0 therefore
fails CPU0's PMA check before it leaves the core, while on CPU1 it goes out
on the bus and the error comes back late.

Setting only CPU1's PMA entry 0 by hand, from user space, on smp-expt made
CPU1's faults precise (40,000 faults for 20,000 iterations).  Every CPU1 run
then completed without an oops: memset faults alone (twice), next to the
`nanosleep()` loop, the ping-pong and the `sched_yield()` loop, and vfork
children next to the `nanosleep()` loop.

The fix (0fbb8e3) copies CPU0's protection to CPU1 in the boot-shim.  Before
starting CPU1, CPU0 saves its 16 PMA entries (configuration and address),
its 16 `pmpaddr` and its 4 `pmpcfg` CSRs.  CPU1 loads them first thing in
`c68_secondary_entry`: each PMA entry is disabled, given its address and
then its configuration, and all `pmpaddr` CSRs are written before the
`pmpcfg` CSRs that lock them.  CPU1 then reads everything back and reports
every bit that differs; the shim prints the result as
`C68 CPU1 PMA/PMP diff=00000000`.  `check-boot-log.py` fails a boot log
with any other value, and one where the shim parked CPU1 (`C68 CPU1
WAITING`) without printing the line; the logs of smp-def, smp-expt and
v0.3.2 fail that check.  Under Linux on smp-prot, both CPUs' PMA and PMP
CSRs read the same.

Results on smp-prot, CPU1 (CPU0 is in the table above):

| Faults, load beside them | Result |
|---|---|
| returning handler (20,000 iterations) | 40,000 faults on CPU1, as on CPU0 |
| memset, none (twice) | 200,000 in 11.86 s, 11.74 s |
| single stores, none | 200,000 in 11.71 s |
| single loads, none | 200,000 in 11.69 s |
| memset, `nanosleep()` loop | 200,000 in 12.53 s |
| memset, ping-pong | 200,000 in 20.16 s |
| memset, `sched_yield()` loop | 200,000 in 22.10 s |
| memset, none, MEXSTATUS read before each fault | 200,000, bit never set |
| vfork children, `nanosleep()` loop | 20,000 in 41.66 s |

No oops, panic or reset.

### Performance (smp-prot against up-prot)

up-prot is smp-prot's tree built with `EASYSTICK_C68_MAXCPUS=1`, so this
compares one CPU with two on the same code.  Each build was measured twice
on one boot, starting five minutes after it, over SSH as `m5`.  Each job ran
alone (x1) and then as two copies at once (x2); the times are wall-clock
seconds from `/proc/uptime`:

- cpu: an awk loop of 400,000 additions;
- fork: a shell loop of 200 fork+exec of `cat /dev/null`;
- mpy: `micropython mpybench.py`, the cases in the second table.

| Job | smp-prot x1 | smp-prot x2 | up-prot x1 | up-prot x2 |
|---|---|---|---|---|
| cpu | 7.17, 7.06 | 8.31, 8.06 | 8.29, 7.97 | 15.97, 16.04 |
| fork | 4.75, 4.77 | 8.73, 8.81 | 4.82, 5.10 | 10.01, 9.96 |
| mpy | 4.32, 4.17 | 5.44, 5.58 | 4.84, 4.69 | 9.55, 9.63 |

`mpybench.py` alone, after those (ms):

| Case | smp-prot | up-prot |
|---|---|---|
| int loop 200k | 1632, 1593 | 1877, 1926 |
| first 1000 primes | 224, 227 | 234, 265 |
| float sum 50k | 406, 401 | 435, 448 |
| string format 5k | 187, 185 | 299, 187 |
| dict insert 5k | 1261, 1263 | 1253, 1463 |
| sha256 256 KB | 67, 68 | 96, 106 |
| alloc 50x100 KB + gc | 364, 363 | 368, 379 |

- Two CPU-bound jobs at once took 1.1 to 1.3 times as long as one on
  smp-prot, and twice as long on up-prot.
- Two fork loops took 1.85 times as long as one on smp-prot (2.0 on
  up-prot): fork+exec gains little from the second CPU.  Why is not known.
- One job alone took 11 to 14 % less time on smp-prot (cpu and mpy; the
  mpybench cases 0 to 36 %).  That fits where it ran.  In three more runs
  of the cpu job (7.10, 7.07 and 7.04 s), CPU1 accrued 89 to 100 % of its
  user time.  CPU0 takes the SDIO host's interrupts (`dw-mci`, about 1,570
  a second with the board otherwise idle on this network) and the tasklets
  and softirqs behind them.  With the board idle, CPU0 was 12 % busy;
  CPU1, which takes only its own timer and IPIs, 0.2 %.  On up-prot a job
  shares CPU0 with that work, and one cpu job there took about as long as
  each of two on smp-prot, where one of them has to run on CPU0.
- A signal delivered to a handler costs more with two CPUs.  On NOMMU the
  kernel writes the `rt_sigreturn` call onto the user stack and flushes the
  instruction cache on every CPU, which with two CPUs takes an IPI and a
  wait for the other CPU.  20,000 iterations of the returning SIGSEGV
  handler (40,000 faults) took 2.69 s on CPU0 and 2.50 s on CPU1 of
  smp-prot, and 1.49 s on up-prot.  0083 (#44) removes the copy and the
  flush: 0.7 s on either CPU (`issue41-44-2026-10-20.md`).
- SSH throughput did not compare the builds: it went at whatever the Wi-Fi
  link allowed.  Three 4 MB downloads in a row from one smp-prot boot took
  83, 75 and 17 s (48, 54 and 242 KB/s), with the CPUs 94 % idle.  The best
  single-session rates were 242 KB/s on smp-prot and 214 KB/s on up-prot.

## USB drive saves rebooted a 2-CPU board (0072)

### Symptom (smp-prot)

Putting `main.py` on the USB drive for the autorun check rebooted the
board, and so did every other change to the drive:

```
boot commit: staged 262144 bytes, crc32=ea205fc3
boot commit: flash write unavailable (Device or resource busy); saved at the next reboot
[bootsync] Staged for the next reboot hash=… (the kernel could not write flash)
[bootsync] Rebooting to commit the image to flash (auto_reboot=no in config.txt turns this off)
The system is going down NOW!
I (4857) easystick-boot: boot update committed: generation=75 slot=1 crc=ea205fc3
```

No edit was lost, since the shim wrote the slot during the reboot, but the
board rebooted and dropped off USB after every save, which the README says
it does not do.  First-boot credentials go through the same helper, so they
stayed in PSRAM until a reboot, and a power cycle before it would have
generated new ones.

### Cause

0072 refused to write flash (`-EBUSY`) when more than one CPU was online.
It erases and programs flash with the ROM's `esp_rom_spiflash` routines on
SPI1, with interrupts off, so that nothing reads flash meanwhile; the only
flash reads at run time are the rootfs through the cache window.  With two
CPUs the other one could read the rootfs, so 0072 left the write to the
shim.  `easystick-boot-commit` then exited 2 (staged only), and bootsync
rebooted (`auto_reboot` is on by default).

### Fix (bcba64e)

Each ROM read, erase and program runs under `stop_machine()`: CPU0 makes
the call with interrupts off while the other CPU spins with interrupts off,
so neither reads flash meanwhile.  On one CPU this is the same
interrupts-off section as before.  Each section is one ROM call, the
longest a 4 KiB erase (about 18 ms).

### Results (smp-bf)

Flashed as above; boot check 13/13.

- Drive save: `boot commit: written to flash`, then `[bootsync] Saved to
  flash`, and no reboot.  The flash record went from generation 75 (slot 1)
  to 76 (slot 0).
- Commit time (`easystick-boot-commit` on a changed copy of the drive image,
  then on the drive image again, timed with `/proc/uptime`; this includes
  staging, the CRC checks, the 256 KiB write and its read-back): 1.84 to
  1.90 s for 8 commits with the board idle.  up-prot (one CPU, 0072 before
  the fix) took 1.72 to 1.80 s for 6, so `stop_machine()` adds about 5 %.
  Reading `boot_commit` (both records and the slots' CRCs) took 0.22 s.
- Under load (the CPU hog killed every 5 s and the MicroPython loop of
  `smpload.sh`, plus a busy loop that ran throughout): 4 commits in 2.08 to
  2.35 s and 2 drive saves, both `Saved to flash`.  MicroPython ran 44 times
  with no allocation failure, the hog was killed 24 times, and the kernel
  logged no oops, BUG or stall.
- First-boot credentials: with `root_password=` removed from

## Review (Devin)

- 0080: correct and sufficient; every other `xmit` and `INT_ENA` user already
  holds `port->lock`; no deadlock (the lock holder never waits for the
  interrupt) and no lost wakeup.
- SMP audit of the board patches and ESP-Hosted: the ACM race was the only
  real cross-CPU defect.  Systimer (`st_lock`), IPI (per-CPU mailboxes), CLIC
  routing, cache sync, GPIO, `esp32_uart`, dwc2 and esp-hosted (one `esp_TX`
  thread) are correct.  Low: the boot-flash commit path has one static sector
  buffer behind a root-only sysfs file (one writer by design); a long console
  dump can hold the port lock for tens of milliseconds; the dw-mmc cmd53
  trace buffer assumes one host.
- The default switch (c87c754): `MAXCPUS` defaults to 2 before every use
  (validation, the DTS and config rewrite, `SOURCE.txt`); `MAXCPUS=1` and
  `IRQ_LEVEL0=0` still work as opt-outs.  A 2-CPU build with
  `IRQ_LEVEL0=0` brings the CPU1 latch back.
- 0081 and the boot-shim fix: the mret sits on the exception path only, so
  each exception runs one; `mcause` = `3 << 28` returns from M to M with
  MIE off and the CLIC level unchanged; every exit path rewrites the CSRs
  from pt_regs.  The shim's CSR numbers match ESP-IDF, the `pmpaddr` CSRs
  are written before the `pmpcfg` CSRs that lock them, and fences order the
  hand-over between the CPUs.  Low: an exception in the entry code before
  the mret still locks up (see Open); `check-boot-log.py` failed a nonzero
  diff but not a missing line (it now fails both).  Info: CPU1 turns off
  PMA entry 15, which covers the code it runs, for three instructions while
  it rewrites it, as ESP-IDF does on CPU0.
- 0072 (bcba64e): with no CPU mask, `stop_machine()` runs the call on the
  first online CPU, CPU0, once every online CPU has turned interrupts off.
  With one CPU online, or without `CONFIG_SMP`, it is the same
  interrupts-off section as before.  The callers hold only a mutex, in
  process context.  Low: a wedged CPU1 would now hang a commit in the sysfs
  write instead of failing it at once with `-EBUSY`; about 1,350
  `stop_machine()` calls per commit cost about 0.1 s, and one per sector
  would cost less but keep interrupts off longer.  Info: between calls
  another CPU may read the rootfs from flash again.  That is safe because
  each ROM erase or program waits for the flash to go idle before it
  returns (ESP-IDF's `esp_rom_spiflash.c`; an erase call takes about 18 ms).

## 0068 correction

The 2026-10-14 record says reading `mintstatus` (0xfb1) or `mintthresh`
(0x347) on the deaf CPU1 "stops the core for good".  It faults instead:

- On e1 boots 0, 6, 7 and 9 the assist_debug samples show CPU1 at that
  `csrr` (`0x4830e208`, sp `48c87ef0`) before and after an extra IPI, with
  the last PC before the exception one instruction earlier, and the read
  never returned a value.
- pstore from another e1 boot holds `Oops - illegal instruction [#1]` for the
  same instruction on CPU1 (`epc 4830e208`, `sp 48c87ef0`,
  `badaddr 34702773`, `cause 30000002`), then
  `Kernel panic - not syncing: Fatal exception in interrupt`.  The idle task
  was not in an interrupt: kernel-mode traps on RISC-V run under
  `irqentry_nmi_enter()`, so `die()` reports every kernel fault that way.

The captures do not show whether the exception is delivered late or only
on some boots.  Either way the read is harmful on a deaf CPU1, and the
panic never reached the serial log, only pstore.  0077 already avoids
`csrr 0xfb1`, which raised the same exception at trap entry during boot,
and 0068 no longer reads either CSR.

## Open

- Not confirmed against ESP32-P4 documentation that `mil` is restored only
  by an `INT=1` mret; the mechanism rests on the captures and on 0079.
- CPU1 cannot be taken offline at run time.  The kernel has
  `CONFIG_HOTPLUG_CPU=y` (`PM_SLEEP_SMP` selects it; the `is not set` line
  in `linux/c68/linux.config.fragment` has no effect), but the spinwait
  boot method has no `cpu_stop`, so CPU1 has no `online` file in sysfs.  A
  1-CPU image needs `EASYSTICK_C68_MAXCPUS=1` at build time.
- An exception in the entry code before the 0081 mret (while the frame is
  saved, for example a store through a bad kernel `sp`) still finds
  EXPT_VLD set and locks the core up.  No software change can close that
  window.
- A kernel `ebreak` in a system call (a WARN) is no longer a double
  exception with 0081; that is not tested.
- A user access that the PMA lets through but that fails on the bus (a hole
  in the peripheral space) would be reported late, as CPU1's stores to
  address 0 were before the boot-shim fix.  That is not tested on either
  CPU.
- While six commits ran back to back, pings were delayed by up to 0.9 s and
  1 to 3 of 65 were lost, on one CPU as on two (see the 0072 section).  Each
  interrupts-off section lasts one ROM call, 18 ms at most, so why replies
  waited that long is not known.  #43 found it: the calls came back to back
  and held the CPUs for nearly the whole commit.  0072 now skips unchanged
  sectors and rests between bursts of calls (`issue41-44-2026-10-20.md`).
