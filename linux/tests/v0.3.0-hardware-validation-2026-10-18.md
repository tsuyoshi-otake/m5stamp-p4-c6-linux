# v0.3.0 hardware validation (2026-10-18)

Board: M5Stamp ESP32-P4 + C6 (SDIO), P4 USB Serial/JTAG on COM10.  Only the
P4 flash was written; the C6 was not touched.  Recovery point: the full
16 MB read-back in `m3-lab-hardware-validation-2026-10-14.md`.

v0.3.0 moves the kernel from Linux 6.18.35 to 7.2.11 (#36).  The 6.18.57
update that came first is in `linux-6.18.57-hardware-validation-2026-10-18.md`.

## What it took to boot 7.2

The first 7.2 builds (CI run 39072874309 and local candidates) stopped right
after `printk: legacy bootconsole [esp32p4usbjtag0] enabled`.  Debug images
with a fault recorder in LP RAM found an instruction access fault in
`early_init_fdt_scan_reserved_mem()`: 7.2 changed `RESERVEDMEM_OF_DECLARE`
to take a `struct reserved_mem_ops *`, and the NOMMU pool patch (0010) still
passed a function, which compiled with a warning only.  The kernel read the
function's first instructions as the ops table and jumped to `0xc4221141`.

The first image that reached userland then showed three more 7.2 changes on
paths that upstream does not test without an MMU:

| Symptom | Cause | Fix |
|---|---|---|
| `boot commit: cannot map PSRAM staging area: Invalid argument`; drive edits not saved; `devmem` fails | `/dev/mem` now uses `mmap_prepare` with a remap action, which the NOMMU backend refuses (`WARNING: mm/util.c`) | 0075: no action on NOMMU; the direct mapping is already at the physical address |
| `PREEMPT_LAZY` selected silently | upstream 7dadeaa6e851 keeps `PREEMPT_NONE` only for `ARCH_NO_PREEMPT` | 0074: select `ARCH_NO_PREEMPT`, pin `CONFIG_PREEMPT_NONE=y` |
| `workqueue: ESP_IF_RX_WORK_QUEUE is using neither WQ_PERCPU or WQ_UNBOUND` | 7.x wants one of the two flags | esp-hosted-ng 0038: `WQ_PERCPU`, the old default |

## Interactive tools and everyday commands

Run as `m5` over SSH on the same image after the checks above
(`cmdcheck.py`: a 120x30 pty for the interactive tools, `exec` for the rest).

| Check | Result |
|---|---|
| `vi` without a file name | screen drawn; insert, `:w /tmp/vt.txt`, `:q`; the file holds the typed line |
| `vi /tmp/vn.txt` | insert, `:wq`; file written |
| `echo hi \| less`, `top -n 1` in the pty | drawn; `q` returns to the shell |
| `python3 -c` with `os`, `json`, `time`, `socket`; `micropython -c` | OK |
| `ls`, `df`, `ps`, `grep`, `sed`, `find`, `awk`, `free`, `uptime`, `pgrep`, `stat`, `diff` + `patch`, `hexdump`, `xxd`, `tar czf`/`tzf`, `gzip -t`, `wget`, `nslookup`, `ip`, `timeout`, `watch` | exit 0 with the expected output |
| `ping 8.8.8.8` | `8.8.8.8 is alive!` |
| `traceroute -m 2 8.8.8.8` as root (serial console) | two hops printed |

Three results that are not 7.2 regressions (the BusyBox and MicroPython
builds are the v0.2.5 ones) and are now stated in the README:

- MicroPython's unix port has no `os.uname()`; the README example used it
  and now uses `platform.platform()`.
- The main BusyBox is built without `FEATURE_FANCY_PING`, so `ping` takes no
  options (`ping -c 2 HOST` prints `bad address '-c'`).
- `traceroute` as `m5` fails with `socket: Operation not permitted`: it
  needs a raw socket, so root only.

## Not covered

- `maxcpus=2`.  The SMP stall of issue #5 was measured on 6.18 and has not
  been re-checked on 7.2; the shipped DTB still boots with `maxcpus=1`.
- Edits from a real Windows/macOS host over USB-A (emulated by a loop mount
  of `/tmp/boot.img` on the board, as before).
- Power loss during a kernel flash write, a soak of hours, and a client
  joining the SoftAP.
