## Source-level review of the IRQ path: the 254 empty callbacks are a host-side loop (2026-08-11)

Nothing was built, flashed, or measured for this section. It is a reading of
the pinned `vendor/linux`, `vendor/esp-hosted` and `vendor/esp-idf` trees
against the marker counts already recorded above, and it changes the
interpretation of three numbers that had been treated as three separate
puzzles. Line numbers cite the unpatched vendor files unless stated otherwise.

### The mechanism

`esp_handle_isr()` reads `ESP_SLAVE_INT_ST_REG`, hands the value to
`esp_process_interrupt()`, then writes *that same value* back to
`ESP_SLAVE_INT_CLR_REG` (`sdio/esp_sdio.c:93-105` after patch 0003).
`INT_CLR` is write-1-to-clear, so a status read of zero produces a write of
zero, which acknowledges nothing.

On the host side `dw_mci_interrupt()` clears its own `RINTSTS` bit and then
masks the per-slot SDIO source inside the hard IRQ handler before queueing
work (`drivers/mmc/host/dw_mmc.c:2917-2921`), and re-arms that mask from
`dw_mci_ack_sdio_irq()` once the callback returns (`dw_mmc.c:1713-1718`).

The two halves form a cycle with no exit: the slave keeps DAT1 asserted
because nothing cleared it, and the host keeps re-arming. One mechanism
reproduces all three recorded observations at once:

| Recorded observation | Explanation under this mechanism |
| --- | --- |
| 254 x SDIO IRQ `status=0x00000000` | the cycle spinning, bounded only by CMD52 round-trip time at 400 kHz |
| `RINTSTS=0x00020000` | slot 1's `SDMMC_INT_SDIO(1)` = `BIT(17)` latched, correctly |
| `MINTSTS=0` | a one-shot sample landing inside the mask window between hard IRQ and ack |

Both register readings are correct and neither is the anomaly. Consequently
**every IRQ-side measurement recorded above is a measurement of this loop, not
of the C6.** That is the reason the telemetry has been stable and uninformative
across seven captures.

### Second defect in the same path

`sdio_claim_irq(func, esp_handle_isr)` is at `esp_sdio.c:731`;
`atomic_set(&context->adapter->state, ESP_CONTEXT_RX_READY)` is at
`esp_sdio.c:797`. The handler's guard (`esp_sdio.c:81-85`) returns early on
`state < ESP_CONTEXT_RX_READY` **without writing `INT_CLR`**, so an interrupt
arriving in that window establishes the same unbounded loop earlier, before
`OPEN_DATA_PATH` is even issued.

Part of that window is safe and part is not, which is worth stating precisely:
`sdio_claim_irq` (731) and `sdio_set_drvdata` (744) both sit inside the
`sdio_claim_host()`/`sdio_release_host()` pair at 717/746, and the MMC core
also claims the host before invoking the callback, so the ISR cannot observe
NULL `drvdata`. The exposed window runs from the `sdio_release_host()` at 746
to the `atomic_set()` at 797.

### Fix

`buildroot-external/package/esp-hosted-ng/0011-easystick-sdio-isr-acknowledge.patch`:

1. Acknowledge with the union of the INT bits `esp_sdio_decl.h` names when
   `INT_ST` reads zero or the read fails, so the host can always break the
   loop. Dispatch still uses the value actually read, so a forced acknowledge
   cannot fabricate an `ESP_SLAVE_RX_NEW_PACKET_INT` event.
2. Split the guard: acknowledge whenever a context exists, and gate only the
   dispatch on `ESP_CONTEXT_RX_READY`.
3. Sample `ESP_SLAVE_INT_RAW_REG` at the head of each empty-status streak
   (first four, then every 256th). A raw latch that `INT_ST` does not report
   means the slave never enabled that source for host delivery - a slave-side
   configuration fault rather than a missing frame. This is the measurement
   the previous telemetry structurally could not make.

Verified only to the extent that source reading allows: the full 0001-0011
series applies cleanly to the pinned `vendor/esp-hosted` host tree with
`patch -p1`, and the result matches the intended file byte for byte. **Not
built, not flashed, not run.**

What the fix cannot do: if DAT1 is held by a source outside the bits
`esp_sdio_decl.h` names, the forced acknowledge cannot clear it and the loop
persists. The `INT_RAW` sample exists to identify exactly that case.

### Three candidate causes checked and closed

Recorded so they are not re-investigated.

| Hypothesis | Verdict | Evidence |
| --- | --- | --- |
| Driver masks/tests `BIT(16)` while Slot 1 raises `BIT(17)` | **ruled out** | `slot->sdio_id = host->sdio_id0 + slot->id`; `sdio_id0` is set only by `dw_mmc-rockchip.c:481`, so it is 0 here, and `snps,slot-id = <1>` makes `SDMMC_INT_SDIO(1) = BIT(17)`. Host and hardware agree. |
| Boot-shim GPIO-matrix routing is incomplete | **ruled out** | `route_input(1..5, 44..48)` matches the P4 Slot 1 signal indices, and `route_input(129, 0x3f)` matches ESP-IDF's own `card_int <- GPIO_MATRIX_CONST_ONE_INPUT` (`esp_driver_sdmmc/src/sdmmc_host.c:788-805`). `card_detect` (127) and `write_protect` (131) are left unrouted, but resolve to the values ESP-IDF selects for the no-CD case, and the DTS sets `broken-cd`/`disable-wp`. |
| Host and slave disagree on the register map (`0x3FF55000` looks like an original-ESP32 base) | **ruled out** | `esp_read_reg()`/`esp_write_reg()` both apply `reg &= ESP_ADDRESS_MASK` (`0x3FF`) before the CMD52 (`sdio/esp_sdio_api.c:108-139`), so only offsets 0x58/0xD4/0x60/0x44 reach the bus. The base is decorative. |

### `slot->id` overloading: resolved, not a suspect

`snps,slot-id = <1>` reaches `slot->id` via WHY2025 patch 0007 and is then
used for six distinct things. Reading each one closes the question rather than
leaving it open:

| Use | Wants | Status |
| --- | --- | --- |
| CMD `card_number` [20:16] (`dw_mmc.c:247,328,370`) | physical 1 | correct - enumeration succeeds |
| `CTYPE` bus-width bit | physical 1 | correct - 4-bit accepted |
| `SDMMC_INT_SDIO` mask/test bit | physical 1 | correct - `BIT(17)` latches |
| `CLKENA` enable bit (`dw_mmc.c:1295`) | physical 1 | correct - `BIT(1)` |
| `CLKENA` low-power bit (`dw_mmc.c:1297,1683`) | physical 1 | correct - `BIT(17)`; see below |
| `CLKDIV` byte index | **logical 0** | the single exception; kernel patch 0009 exists for it |

The `CLKEN_LOW_PWR` case had been left as an open worry - that idle clock
gating might stop the card clock and prevent DAT1 sampling. Source closes it:
`dw_mci_prepare_sdio_irq()` sets `DW_MMC_CARD_NO_LOW_PWR` and clears
`SDMMC_CLKEN_LOW_PWR << slot->id` at claim time (`dw_mmc.c:1650-1677`), and
`dw_mci_setup_bus()` honours that flag on every later clock change
(`dw_mmc.c:1295-1297`). No instrumentation is needed; **do not add a `CLKENA`
log for this reason.**

Kernel patch 0009's reasoning was also verified against the code rather than
taken from its own comment: `mci_writel(host, CLKSRC, 0)` at `dw_mmc.c:1278`
keeps both slots on divider 0, and three separate timeout calculations read
`mci_readl(host, CLKDIV) & 0xff` unconditionally (`dw_mmc.c:383`, `1325`,
`2053`). Writing the divider to byte 1 would leave all three reading a stale
byte 0. 0009 now names 0007 as the patch it partially reverts, so neither
reads as a standalone no-op.

`esp_reset()` returns before logging once the pin is invalid by default. Its
absence is not a regression.

### Patch 0011: the empty-IRQ loop stops

| | PIO baseline | This capture |
| --- | ---: | ---: |
| raw ISR lines | 508 | 4 |
| distinct callbacks | 254 | **2** |
| distinct before `probe completed` | 11 | 2 |
| distinct after `probe completed` | **243** | **0** |
| last ISR line | 759 of 760 | 245 of 271 |

The baseline capture *ended while the storm was still running*. This one runs to
its natural end - `wlan0 did not appear during first-boot DHCP window` at line
271 - with no callback after probe at all. The two callbacks it does contain sit
at lines 242-245, i.e. immediately after `OPEN_DATA_PATH write completed: ret=0`
(238-239) and inside the first 300 ms polling interval; the remaining 2.4 s of
polling and everything after `ESP SDIO probe completed` (264-265) are silent.

Three checks rule out the cheap alternative explanations:

- **Not rate-limiting.** 0011 prints the first four of a streak
  (`empty_isr_streak < 4`). The streak reached only 1, so streak=2 and streak=3
  would have printed had they occurred.
- **Not an unloaded driver.** No `rmmod`, no unload, and no
  `Oops`/`BUG:`/`panic`/`WARNING:` anywhere in the log, so the ISR stayed
  registered on function 1.
- **Not a different window.** Both counts are taken across the same probe
  window, delimited by the same two log markers.

### `INT_RAW` and `INT_ST` are both genuinely zero

The capture contains exactly two distinct ISR records, and they are the whole of
the evidence:

```
esp32_sdio: esp_handle_isr: SDIO IRQ empty: streak=0 st_ret=0 raw=0x00000000 raw_ret=0 dispatch=1
esp32_sdio: esp_handle_isr: SDIO IRQ empty: streak=1 st_ret=0 raw=0x00000000 raw_ret=0 dispatch=1
```

`st_ret=0` and `raw_ret=0` mean neither register read failed, so these are real
zeros and not error sentinels - which is precisely the distinction 0011 was
written to make, since it reports the return code beside the value. The
nonzero-status path never fired: `SDIO IRQ received: status=` is 0 / 0, and
`raw=0x[^0]` and `status=0x[^0]` match nothing in either capture.

The pre-registered branch - *`INT_RAW` nonzero while `INT_ST` stays zero implies
a C6/slave-side interrupt configuration problem* - therefore **does not apply**.
`INT_RAW` is the pre-mask raw status, so zero there means no interrupt event
exists at the source, and a mask or enable misconfiguration on the C6 is
**refuted** rather than supported. This also closes the ambiguity left open in
the previous section: the loop was equally consistent with a genuine C6
interrupt whose cause `INT_ST` does not report *and* with a spurious assert, and
the `INT_RAW=0` sample selects the second.

### Packet length stays zero, by two independent observers

| Marker | Raw / distinct | Values |
| --- | ---: | --- |
| `BOOT_POLL` | 20 / 10 | `iter=0..9`, `elapsed_ms=0..2700`, every one `len=0 ret=0` |
| `BOOT_CMD53_RX` | 2 / 1 | `len=0 ret=0`, after `probe completed` |

All eleven reads returned `ret=0`: the register path works and the zero is the
value, not a failure. Because the polled `PACKET_LEN` path is structurally
independent of the interrupt path, this also disposes of the one real risk in
0011's design - that its forced `INT_CLR` write might destroy a pending event
before anything sees it. Nothing was pending across 2.7 s according to a second
observer that does no clearing at all.

### Unchanged negatives, and one non-regression

`RX_NEW_PACKET` 0 / 0. ESP boot-up event 0 / 0. `ESP-Hosted Version` 0 / 0. No
`wlan0`; the rootfs reports `M3-lab: no wlan0; SSH remains disabled`.

`esp32_sdio mmc0:0001:2: probe with driver esp32_sdio failed with error -22`
(lines 266-267) appears 2 / 1 in **both** captures and names SDIO **function
2**; function 1 binds successfully in both. It is pre-existing and must not be
attributed to 0010 or 0011.

### Where this leaves the blocker

The host side is now clean and, for the first time, uninteresting: enumeration
succeeds, every SDIO register read returns `ret=0`, and the interrupt storm is
acknowledged away. Two of the three host-side puzzles recorded earlier are
closed, and the third - `RINTSTS`/`MINTSTS` - was already shown correct by
construction.

What remains is C6-side, and the `INT_RAW=0` result narrows it: **this is not an
interrupt-configuration fault.** The C6 asserts no interrupt at the raw level
and never presents a nonzero packet length, i.e. it never produces a boot frame
at all. Remaining hypotheses, cheapest discriminator first:

1. The C6 is not running an ESP-Hosted-NG **SDIO slave** build of a matching
   version. Confirm from the image's own `sdkconfig`/artifact metadata, never
   from a release name.
2. The C6 is held in, or repeatedly entering, reset.
3. The C6 boots and its transport initializes, but the slave never reaches the
   point of queueing the bootup event.

Separating these requires C6-side observation. The largest blind spot recorded
above is unchanged: **the C6 has still never been observed directly**, and a C6
that panics early, or that received an SPI-transport build, would produce
telemetry indistinguishable from all eight captures now recorded here.

### What this capture cannot see

- Any C6-side state. No C6 console was attached and the C6 was not reflashed.
- Whether the host SDIO IRQ remained enabled for the whole 60 s. The claim made
  here is narrower: same probe window, same conditions, 254 distinct callbacks
  became 2.
- Anything about the DMA path. `easystick,force-pio` is active, and the only run
  that ever produced `wlan0` used the internal DMA controller.
- A boot frame arriving later than the 60 s capture window.
- Anything at a higher bus rate: `max-frequency = <400000>` still pins the bus
  at the SD identification clock.
- Whether patch 0011 would still be correct once a real interrupt exists. Its
  forced `INT_CLR` write has only ever been exercised against an all-zero
  status.
