# M1 build evidence — 2026-08-09

This record covers host-side compilation and preflight only. No image was
flashed to the connected Stamp-P4, so it is not evidence of an M1 Linux boot,
serial login, or cold-boot acceptance cycle.

## ESP-IDF boot shim

- Container: `espressif/idf:v5.5.3` (ESP-IDF v5.5.3)
- Target: `esp32p4`
- Source: `firmware/linux/boot-shim/` copied into a disposable container
  build directory
- Commands:

  ```bash
  source /opt/esp/idf/export.sh
  idf.py set-target esp32p4
  idf.py build
  ```

- Result: `Project build complete`
- Generated app: `easystick_stamp_p4_boot_shim.bin`, `0x33930` bytes
- The custom `factory` app partition is `0x80000` bytes, leaving `0x4c6d0`
  bytes (60%) free according to ESP-IDF's size check.
- The build emitted only the expected deprecation notices for old watchdog
  Kconfig aliases; it did not run `idf.py flash` or any write operation.

## Buildroot M1 preflight

With the locked external source cache, the non-writing command below passed:

```bash
bash firmware/linux/build-m1.sh /external/path/easystick-p4-src \
  /external/path/easystick-p4-build --print-only
```

It validated the five source pins, staged the project-owned kernel patches,
DTS, and NOMMU configuration, and printed the three Buildroot commands it
would execute. The candidate flash map verifier also passed (16 MiB bound,
non-overlapping regions, no artifact write gate).

The same locked external cache then completed a full Buildroot run in a
disposable Debian container after installing the documented host dependencies.
